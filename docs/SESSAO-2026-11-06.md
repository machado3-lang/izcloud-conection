## 3. Primeiro passo de amanhã: VPS

No console/VNC da VPS (root):

```bash
apt-get update
apt-get install -y socat
```

> O erro anterior foi digitar `install -y ...` sem o `apt-get` na frente. Se
> `apt-get` não existir, use `apt update` e `apt install -y socat`. Não digite
> `install` sozinho.

Depois, duas opções:

### Opção A — copiar o script do projeto

No seu PC:

```powershell
scp C:\Producao\iZCloud\deploy\vps-relay.sh root@IP_DO_VPS:/root/
```

Na VPS:

```bash
bash /root/vps-relay.sh
```

### Opção B — criar o serviço manualmente

```bash
cat >/etc/systemd/system/izcloud-relay.service <<'EOF'
[Unit]
Description=iZCloud L4 relay 443 -> Railway TCP proxy
After=network.target

[Service]
ExecStart=/usr/bin/socat -d -d TCP-LISTEN:443,fork,reuseaddr TCP:zephyr.proxy.rlwy.net:48331
Restart=always
RestartSec=3
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable --now izcloud-relay
systemctl status izcloud-relay
```

Firewall:

```bash
ufw allow 22/tcp
ufw allow 443/tcp
ufw enable
ufw status
```

E liberar **TCP 443 de entrada** no painel do provedor.

Testes:

```powershell
# no PC
Test-NetConnection IP_DO_VPS -Port 443
```

```bash
# na VPS
openssl s_client -connect IP_DO_VPS:443
journalctl -u izcloud-relay -f
```

## 4. Railway: confirmar o canal

No serviço do iZCloud, conferir:

```env
IDCLOUD_PORTA=443
IDCLOUD_BIND=0.0.0.0
IDCLOUD_CERT_PEM=<conteúdo do cert.pem>
IDCLOUD_KEY_PEM=<conteúdo da chave.pem>
```

- O log deve mostrar `[idcloud] ouvindo 0.0.0.0:443` e `[idcloud] canal ativo em 443`.
- O TCP Proxy (`zephyr.proxy.rlwy.net:48331`) deve apontar para a porta interna **443**.
- Se não houver certificado, gerar self-signed (o REP não valida a CA):
  ```bash
  openssl req -x509 -newkey rsa:2048 -nodes \
    -keyout chave.pem -out cert.pem -days 3650 -subj "/CN=izcloud"
  ```
  e colar o conteúdo nas variáveis `IDCLOUD_CERT_PEM`/`IDCLOUD_KEY_PEM`.

## 5. REP-C: configurar e cadastrar

No `REPCONFIG.exe` (ou na tela do REP):

- **iDCloud**: `enable=true`;
- **IP do iDCloud**: **IP público do VPS** (IPv4 literal);
- porta: **443 fixa** (o firmware não tem campo de porta).

No iZCloud, cadastrar o REP (via UI aba **REPs** ou `test_izcloud.mjs` opção 10):

```json
{
  "serial": "00014003750029470",
  "Nome": "REP iDClass 1510",
  "IpAddress": "192.168.100.132",
  "Porta": 5432,
  "Passcode": "admin",
  "REPType": "1510",
  "ModoConexao": "rep_empurra"
}
```

> `ModoConexao=rep_empurra` evita o pull pela nuvem. Quem inicia é o REP,
> através do VPS.

## 7. Pendências locais (opcionais)

- **MySQL local:** para rodar `npm start` na LAN e testar o REP-C por
  `nuvem_puxa`, aponte o `.env` para o MySQL público da Railway:
  ```env
  IDCLOUD_HOST=<host-publico-do-mysql>
  IDCLOUD_PORT=<porta-publica>
  IDCLOUD_USER=root
  IDCLOUD_PASS=<senha-do-mysql-railway>
  CORE_DB=izcloud_core
  ```
  Ou suba um MySQL local via `docker-compose up -d mysql` (banco vazio; teria
  que recriar conta/empresa). **Não versionar o `.env`.**
- **Volume do AFD na Railway:** `data/afd` é efêmero. Para produção, anexar um
  volume em `/app/data/afd` ou definir `IZCLOUD_AFD_DIR`.
- **Teste local `nuvem_puxa`:** com o iZCloud na LAN, cadastrar o REP com
  `ModoConexao=nuvem_puxa` e usar a opção 8 (pull direto do REP) para validar
  o caminho de geração/armazenamento.

## 8. Lembretes importantes

- **iDFace** continua direto na Railway (push HTTPS). O VPS é **só para o REP-C**.
- O REP-C conecta por **IPv4 literal**, **porta 443 fixa**, TLS 1.2 sem SNI/Host.
- O relay do VPS é um **TCP puro na 443**; o `idcloudServer` tem trava de serial.
  Se o IP do cliente for fixo, restrinja a 443 no firewall para esse IP.
- O iZCloud é **coletor + repositório + provedor de AFD**. O REP-P/PTRP
  (MultiPonto) é quem trata jornada e emite AFDT/ACJEF/AEJ; INPI e assinatura
  digital ficam para o MultiPonto.
- **Nunca** commitar `.env`, senhas, tokens ou o dump do iDFace.
