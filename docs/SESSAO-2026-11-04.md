## 2. O que foi implementado

### 2.1 Painel e Coletas (502 em produção)

- `server.js`: `app.use('/api/painel', authTenant)` e
  `app.use('/api/coletas', authTenant)`.
- Antes, sem o middleware, `req.db`/`req.tenant` chegavam `undefined` e as duas
  rotas respondiam 502. O Painel é a primeira tela do cliente.
- Depois do deploy: sem token deve dar 401/400; com token + `X-Empresa`, 200.

### 2.2 Canal iDCloud

| Item | Correção |
|---|---|
| Schema da coleta | `ctx.schema` vem da vaga/tenant, não do serial |
| Vaga | guarda `schema`, `serial` e `passcode`; casa pelo `nSerie` |
| Vaga manual | `POST /api/reps/:id/reservar-coleta` carrega o tenant e o serial |
| Auto-aceite | REP com `Serial` já cadastrado é aceito sozinho (`IDCLOUD_AUTOACEITE=true`) |
| `get_about` | firmware v1048 **exige sessão**: o canal faz `login` antes |
| Allowlist | `COMANDOS` agora é verificada em `pedir()` |
| `rep_coletas` | `id_reps` virou `BIGINT` + migração automática |
| `rep_coletas` SQL | `INSERT` com 6 colunas/6 valores |
| Bind | novo `IDCLOUD_BIND` (não reutilizar `IDCLOUD_HOST`, que é o MySQL) |
| TLS | aceita `IDCLOUD_CERT_PEM`/`IDCLOUD_KEY_PEM` (Railway sem volume) |
| Tenants antigos | `migrarTenantsExistentes()` roda no boot |

### 2.3 AFD completo

- O canal sempre mandava `limit: 1000`. Agora, por padrão, **não manda `limit`**.
- `IDCLOUD_AFD_LIMIT` permite voltar ao comportamento antigo (ex.: 1000).
- Timeout de `get_afd` subiu para 120s; `load_users` com templates para 60s.
- Gravação em **lote de 500** e com `desdeNsr` (não reprocessa o histórico).
- `sync.js` (poller `nuvem_puxa`) também usa o `salvarAfd` em lote.

### 2.4 Importação da empresa/funcionários/biometria do REP

- Novo módulo `importarRep.js`: lê `load_company` + `load_users?templates=true`
  e grava empresa (`empregadores`), funcionários, vínculos (`equip_pessoa`) e
  biometria (`templates`).
- `POST /api/reps/:id/importar`: usa IP/porta/Passcode já cadastrados no REP.
- Botão **Importar** na lista de REPs e **Importar empresa e funcionários do
  REP** na aba Funcionários.
- `POST /api/pessoas/importar` (versão explícita, com IP/senha no corpo) também
  importa a empresa.
- **Primeiro contato pelo canal**: se a empresa ainda não tem funcionários,
  `coletar` faz a importação inicial (`IDCLOUD_IMPORTAR_AUTOMATICO=true`).
- Usuários de **número curto** (`pis=1`, `123`, `54321`) são ignorados: são
  código iDCloud/teste, não funcionários.
- Cadastro completo: nome, PIS/CPF, código, matrícula, senha, admin, RFID,
  barras e templates.
- `templates` grava `dados` **e** `Template` (contrato iDCloud).
- Empresa preenche `tipo_documento`/`cnpj`/`cei`/endereço **somente se vazio**.

### 2.5 Cadastro manual + envio ao REP

- `POST /api/pessoas` **salva na nuvem primeiro** e só depois tenta enviar.
- Se o REP estiver inacessível, o cadastro não é perdido; a resposta traz
  `erroEnvio`.
- `gravarPessoa` faz **upsert por PIS/CPF** (não duplica).
- UI: seletor de REP opcional no cadastro de funcionário; o envio usa o
  IP/porta/Passcode salvos no equipamento.
- **Enviar vinculados ao REP** usa o cadastro do REP, sem redigitar conexão.
- `enviarUsuarios` normaliza `nome/matricula/codigo/senha` (UI) para
  `name/registration/code/password` (firmware).

### 2.6 Empresa: CNPJ/CPF, CEI e responsável

- `izcloud_core.clientes` ganhou:
  - `tipo_documento ENUM('CNPJ','CPF')`;
  - `cei VARCHAR(20)`;
  - `cnpj` guarda CNPJ **ou** CPF, conforme o tipo.
- `responsavel_nome`/`responsavel_cpf` já existiam e foram mantidos.
- Migração automática no boot para bancos existentes.
- API: `POST/PUT /api/empresas`, `/api/admin/empresas`,
  `/api/admin/contas` e `/api/auth/register` aceitam os campos.
- UI do cliente e painel administrativo atualizados.
- Importação do REP (`load_company`) preenche os campos vazios.

### 2.7 Firmware: 418, não 1048

- A API devolve `versionFW=1048` (decimal); o display mostra `418` (`0x418`).
- `probe` agora devolve `firmwareDisplay` e `mrpDisplay`.
- UI mostra **Firmware: 418 (0x418)** e **MRP: 618**.
- Validado no REP real.

### 2.8 AFD import/export

- Nova aba/cartão **Importar arquivo AFD** na aba AFD: aceita AFD 1510 (PIS) e
  671 (CPF), inclusive gerado pelo iDFace.
- Exportação ganhou seletor de **formato 1510/671**.
- `painel` agora casa o documento por **PIS ou CPF** (ranking de 671 funcionava
  vazio antes).
- Limitação: o exportador gera header tipo 1 + batidas tipo 3 + trailer tipo 9;
  **não regenera o registro tipo 2 do empregador** (CNPJ/CPF + CEI + razão
  social) do arquivo original. Ver §6.

### 2.9 iDFace — análise e diagnósticos

- Documento [`IDFACE.md`](IDFACE.md) com o que existe em
  `idacessoweb`, `controle-de-acessos` e `sistema-de-pontos`.
- `test_idface.mjs`: diagnóstico **somente leitura** do iDFace.
- `test_idface_push.mjs`: capturador de push (query, headers e corpo) e teste
  do formato oficial de comando.
- O que reaproveitar: proxy FCGI, `configurePush` (`push_server`), upload

## 3. Validação no REP real

Ambiente: `192.168.100.132`, **web server na porta 5432**, `admin/admin`.

### 3.1 Identificação

```json
{
  "serial": "00014003750029470",
  "firmware": 1048,
  "firmwareHex": "0x418",
  "firmwareDisplay": "418",
  "mrp": 1560,
  "mrpDisplay": "618",
  "portaria": "1510",
  "usuarios": 21,
  "templates": 34
}
```

- `get_about` **sem sessão** responde 401 (`Invalid session`). Com sessão,
  devolve serial/firmware. O canal antigo chamava antes do login e nunca
  identificava o aparelho.
- `get_system_information` → `user_count=21`, `template_count=34`,
  `last_nsr=38539`.

### 3.2 AFD

| Chamada | Resultado |
|---|---|
| `get_afd` com `limit: 1000` | 1.001 linhas / 942 batidas / 43.622 bytes |
| `get_afd` **sem `limit`** | **38.543 linhas / 37.925 batidas / 1.541.609 bytes** |
| `get_afd` com `limit: 2000` | HTTP 400: `'limit' máximo é 1000` |

Confirmado: o arquivo inteiro vem sem `limit`. O `repClient.baixarAfd` também
devolveu as 38.543 linhas.

> Os números crescem com o uso: uma segunda execução já mostrou **38.545
> linhas** e `last_nsr=38541`. O que importa é que sem `limit` vem o arquivo
> inteiro; com `limit: 1000` vêm só as primeiras 1.001 linhas.

### 3.3 Empresa (`load_company`)

```json
{
  "name": "FERNANDO DE CASTRO",
  "address": "GRANJA NOSSA SENHORA APARECIDA, S/N. - GLEBA UBIRATAN - IVINHEMA - MS",
  "cpf": 1,
  "tipo_doc": 2,
  "cpf_cnpj": 27233456100,
  "cei": 0
}
```

### 3.4 Funcionários (`load_users`)

- 21 usuários; `limit` máximo 100; `offset` funciona; `count` total.
- `templates: true` devolve array de strings base64.
- 18 funcionários reais + 32 templates; 3 usuários curtos/teste ignorados:
  - `ADMIN` (pis=123)
  - `TESTE IDCLOUD ZC` (pis=54321)
  - `TESTE` (pis=1)

### 3.5 Envio de funcionário novo

Confirma o fluxo "cadastrar na nuvem e enviar ao REP a qualquer momento".
