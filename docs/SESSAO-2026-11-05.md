## 3. AFD do iDFace — endpoint real

A interface web (`/reports/afd`) usa:

- **595 (PIS)** → `POST /export_afd.fcgi?session=<session>` sem `mode`
- **671 (CPF)** → `POST /export_afd.fcgi?session=<session>&mode=671`

Corpo:

- Integral: `{}`
- Por NSR: `{ "initial_nsr": N }`
- Por data: `{ "initial_date": { "day": D, "month": M, "year": Y } }`

A resposta é `text/plain` com o AFD. O download da UI usa o nome
`AFD_Report_<595|671>_<integral|nsr|data>_<data>_<hora>.txt`.

O iDFace chama o layout PIS de **595**; o conteúdo é o mesmo do 1510. O iZCloud
trata **595 como alias de 1510** no parser, na sincronização e na exportação.

Medição de 05/11/2026 **com 2 marcações reais** (usuário `ANTONIO TESTE`,
`id=70175681172`, `registration=02613449424`):

| Modo | Bytes | Linhas | Batidas | Tipos |
|---|---|---|---|---|
| 595 (PIS) | 475 | 5 | **2** | 0:2, 1:1, 3:2 |
| 671 (CPF) | 574 | 5 | **2** | 0:2, 1:1, 3:2 |

Linhas tipo 3 medidas:

```text
595: 00000000130511202610200701756811724A72
671: 00000000132026-11-05T10:20:00-0400070175681172ADB4
```

O que isso confirma:

- O documento no AFD é o **`id` do usuário** (`70175681172`), **não** a
  `registration` (`02613449424`).
- No 595/PIS o documento vai com 12 dígitos (`070175681172`, zero à esquerda).
- No 671/CPF o iDFace também manda **12 dígitos** (`070175681172`) antes do CRC,
  diferente do layout padrão de 11 dígitos. O parser antigo lia
  `substring(34,45)` e devolvia `07017568117` (perdia o último dígito).
- O AFD do iDFace **não tem registro tipo 2 (empregador) nem tipo 5
  (empregados)**: tem cabeçalho tipo 1, marcações tipo 3 e a linha de trailer
  `999999999...9`. O empregador/CEI continua sendo cadastro manual no iZCloud.
- O AFD do iDFace já vem completo o suficiente para importar as batidas; não
  precisamos sintetizar AFD a partir de `access_logs`.

### 3.1 Correção aplicada no parser

`afd.js` ganhou `extrairDocumento(linha)` e passou a:

- no 671, pegar tudo antes do CRC (4 chars) e remover o zero de preenchimento;
- no 595/1510, pegar o PIS em 22-34 e remover o zero de preenchimento;
- `idcloud.js` (gravação do AFD) e `parseLinhaBatida` usam o mesmo helper.

Testes: `test/afd.test.mjs` cobre as duas linhas reais do iDFace e o layout
padrão de 11 dígitos. `npm test` passa.

### 3.2 Automação recomendada

1. Chamar `export_afd.fcgi` no iDFace com `mode=671` ou sem `mode` (595).
2. Salvar o arquivo bruto em `data/afd/<tenant>/` (auditoria/download).
3. Importar as linhas tipo 3 com `salvarAfd` (já corrigido) e atualizar
   `sync_status`/`rep_coletas` com o maior NSR.
4. Usar `initial_nsr` para coletas incrementais.

### 3.3 Onde estão PIS/CPF no iDFace (a “charada”)

Consulta somente-leitura no iDFace (05/11/2026):

```json
// users
{"id":70175681172,"registration":"02613449424","name":"ANTONIO TESTE",...}

// c_users (campo customizado "CPF")
{"c_users":[{"id":1,"user_id":70175681172,"cpf":"19373613065"}]}

// custom_columns
{"custom_columns":[{"id":1,"custom_table_id":1,"column_name":"cpf","name":"CPF"}]}
```

Ou seja:

| Dado | Onde está |
|---|---|
| **PIS** | `users.registration` = `02613449424` |
| **CPF** | `c_users.cpf` = `19373613065` (campo customizado) |
| **ID do usuário** | `users.id` = `70175681172` (gerado pelo equipamento) |

O relatório AFD do iDFace **não junta** `users.registration` nem
`c_users.cpf`: ele usa **`users.id`** nos dois formatos (595 e 671). Por isso
ambos saíram com `70175681172`. A diferença 595 × 671 é só de **layout**
(PIS/data clássica × CPF/ISO), não de campo de origem.

### 3.4 Teste com o RHiD (antes de implementar)

Para descobrir como o iDFace oficial trata isso, o próximo passo é configurar
o mesmo equipamento em uma conta **RHiD da ControlID**, subir o usuário por lá
e comparar:

1. **Antes do RHiD** — rodar agora e guardar:
   ```bash
   node test_idface_dump.mjs 192.168.100.138 80
   ```
   Gera `idface_dump_<timestamp>.json` com `users`, `c_users`,
   `custom_columns`, `access_logs`, `system_information`, config e AFD
   595/671 (somente leitura).
2. Configurar o equipamento no RHiD e subir o usuário com PIS/CPF.
3. **Depois do RHiD** — rodar o dump de novo.
4. Baixar o AFD 595 e 671 **do equipamento** e **do RHiD**.
5. Comparar:
   - `users.id` mudou para o PIS/CPF? Foi criado outro usuário?
   - `users.registration` / `c_users.cpf` mudaram?
   - O AFD do RHiD usa PIS/CPF ou `users.id`?
   - O AFD do equipamento continua com `users.id`?

Resultados possíveis e o que fazer:

- **RHiD grava `users.id` = PIS/CPF** → o iZCloud deve provisionar o usuário
  com `id` = PIS (595) ou CPF (671); como um usuário só tem um `id`, talvez
  sejam necessários dois cadastros ou reescrita do AFD.
- **RHiD gera o AFD na nuvem** com o PIS/CPF do banco dele → o iZCloud precisa
  fazer o mesmo: mapear `users.id` ↔ PIS/CPF e reescrever as linhas tipo 3
  (e o CRC) ou gerar o AFD a partir dos `access_logs`.
- **RHiD usa o `users.id` e mapeia no software** → o iZCloud pode aceitar o
  AFD bruto e fazer o de/para na importação/exportação.

**Não implementar a coleta/reescrita de AFD antes desse comparativo.**

### 3.5 Resultado do comparativo com o RHiD (05/11/2026)

O teste foi feito e o resultado está detalhado em
[`RHID-COMPARATIVO.md`](RHID-COMPARATIVO.md). O que importa:

- **O que o RHiD fez no equipamento:** apagou o usuário `id=70175681172` e criou
  outro com `id=2613449424` (PIS `02613449424` sem zero à esquerda). Por isso as
  marcações novas saem com PIS no AFD do equipamento. `c_users.cpf` ficou vazio e
  `registration` virou `"2"` (matrícula interna do RHiD).
- **Marcações perdidas:** as 4 primeiras (com o `id` antigo) não aparecem no AFD,
  AFDT, ACJEF nem AEJ do RHiD. Só as 2 de 11:59 (já com PIS) entraram.
- **Arquivos fiscais são gerados na nuvem pelo RHiD:**
  - **AFD 671 v004**: tipo 5 (empregados) + tipo 7 (marcações REP-P), **CPF**,
    hash SHA-256 e assinatura P7S;
  - **AEJ 671**: tipos 01/03/04/05/07/08/99, **CPF**;
  - **AFDT 1510** e **ACJEF 1510**: **PIS**, para compatibilidade.
- **O “AFD 1510” do RHiD não existe:** o arquivo `AFDBR5120...REP_P.txt` é um
  **AFD 671 v004**, não 1510. Os artefatos 1510 são o AFDT e o ACJEF.
- **Tratamento REP-P:** as 2 marcações de 11:59 foram marcadas como `D`
  (`Entrada duplicada` / `Entrada sem saída`) no AEJ e no AFDT. O REP-P não é só
  armazenar batidas; ele trata jornada.
- **Decisão de arquitetura:** iDFace = coletor; iZCloud = coleta + cadastro +
  armazenamento; os fiscais são gerados na nuvem por um REP-P/PTRP. **Não
  reescrever o AFD do equipamento.** O vínculo `device_user_id` ↔ funcionário
  precisa ser versionado (`valid_from`/`valid_to`) para não perder marcações
  quando o `users.id` mudar.
- **Alerta legal:** a Portaria 671 exige, para REP-P, registro no INPI,
  assinatura ICP-Brasil e Atestado Técnico/Termo de Responsabilidade
  (arts. 78, 88 e 91). Gerar o arquivo no layout certo não homologa o sistema.

## 4. Push do iDFace — VALIDADO em 05/11/2026

Teste autorizado, feito com o capturador local + **Cloudflare Quick Tunnel**
(HTTPS válido, sem firewall/admin). O iDFace foi apontado para o túnel,
recebeu um comando e a configuração foi **restaurada** no final.

### 4.1 O que o iDFace enviou

```text
GET /push?deviceId=4408801109364847&uuid=4fa06cbe
```

- **`deviceId` = 4408801109364847** (igual ao `device_id` do
  `system_information`) — identificador estável.
- **`uuid` = 4fa06cbe` (e depois `ca1abe36`) — muda a cada poll; NÃO é
  segredo/token. Não usar como autenticação.
- Não veio `serial`, `iDCloud_code` nem header `X-Device-Serial`.
- O IP público do cliente veio nos headers do Cloudflare
  (`cf-connecting-ip`), mas não é estável.

O servidor respondeu com o comando oficial **single**:

```json
{
  "verb": "POST",
  "endpoint": "message_to_screen",
  "body": { "message": "Teste iZCloud", "timeout": 5000 },
  "contentType": "application/json"
}
```

O iDFace executou e respondeu:

```text
POST /result?deviceId=4408801109364847&uuid=4fa06cbe&endpoint=message_to_screen
body: {"response":"{}"}
```

Ou seja: **o formato single `{verb, endpoint, body, contentType}` funciona**.
O `message_to_screen` é um bom teste inofensivo (mensagem na tela). No segundo
poll o servidor respondeu `{transactions:[]}` e o aparelho ainda postou
`/result` com `{"transactions_results":[]}`.

### 4.3 Dados via push (o ponto decisivo)

Também testamos comandos de leitura/exportação via push:

| Comando | Resultado |
|---|---|
| `load_objects` `{object:'access_logs',limit:5}` | `/result` com `response` JSON contendo os `access_logs` |
| `export_afd` `{}` | `/result` com o **AFD 595 completo** (header + tipo 3 + trailer tipo 9) |
| `export_afd` + `queryString:'mode=671'` | `/result` com o **AFD 671 completo** (ISO/CPF) |

Exemplo de resultado do `export_afd` 671 (4 marcações após os testes):

```text
000000000110...ControliD...04408801109364847...
00000000132026-11-05T10:20:00-0400070175681172ADB4
00000000232026-11-05T10:27:00-04000701756811720072
00000000332026-11-05T10:44:00-0400070175681172D036
00000000432026-11-05T10:45:00-0400070175681172FDD7
99999999900000000000000000400000000000000000000000000000000000009
```

Detalhe importante: o modo 671 tem de ir em **`queryString: 'mode=671'`** no
comando. Colocar `export_afd?mode=671` no campo `endpoint` fez o aparelho
devolver a página HTML da interface, não o AFD.

**Consequência:** o iDFace pode ser 100% nuvem via push. Não precisa de IP
fixo, VPS nem acesso entrante. O servidor enfileira `export_afd`/`load_objects`
e recebe o resultado no `/result`.

### 4.2 Conclusões para a implementação

1. **Identificação:** usar `deviceId` (estável) + o `iDCloud_code` como
   **código de claim** informado pelo técnico/admin. O push não envia o
   `iDCloud_code`; ele é lido no `system_information` ou digitado na tela.
2. **Autenticação:** como o push só manda `deviceId`/`uuid`, colocar um
   **token por dispositivo no path da URL** de push
   (`https://.../api/idface/<token>`). O técnico configura essa URL no
   aparelho; o servidor valida o token antes de responder. Sem token, apenas
   registra o dispositivo como “pendente”.
3. **Fila:** persistir comandos por `deviceId` e entregar um comando por poll
   (single). O formato batch também existe, mas o single já foi validado.
4. **Resultado:** persistir `POST /result` (deviceId, uuid, endpoint,
   response/error) para auditoria e para saber se o comando foi executado.
5. **Transporte:** o iDFace aceita URL/domínio com HTTPS válido. A Railway
   serve; o Cloudflare Tunnel também. Não precisa de IP fixo/VPS para o iDFace.
6. **Configuração:** não enviar `push_attributes` neste firmware; usar só
   `push_remote_address`, `push_request_timeout`, `push_request_period`.
7. **Restauração:** após o teste, a config voltou para
   `https://izcloud.com.br`, timeout `30000`, period `300`. O monitor ficou no
   servidor oficial da ControlID.

## 5. VPS de $3 (InterServer) para o REP iDClass

O plano de **$3/mês** da InterServer (1 slice) oferece:

- 1 core, **2GB de memória**, 40GB SSD, 2TB de transferência;
- **endereço IP público estático**;
- acesso root, KVM;
- regiões nos EUA (NYC, Dallas, Los Angeles);
- cobrança mensal, **sem trial/money-back**.

**Serve para o REP iDClass?** Sim, como **relay L4**:

```
REP iDClass (TLS 1.2, 443, sem SNI/Host)
        │
        ▼
VPS IP fixo:443  (nginx stream ou socat — TCP puro)
        │
        ▼
Railway TCP Proxy  →  idcloudServer (IDCLOUD_PORTA interna)
```

Pontos de atenção:

- Confirmar que o provedor permite **TCP 443 de entrada** (normalmente sim;
  verificar firewall/security group).
- O relay tem de ser **L4**, não Caddy/nginx L7: o REP não manda SNI/Host.
- O IP precisa ser **estático** (a página diz "static public IP addresses").
- 2GB é suficiente para o relay e até para uma instalação pequena do iZCloud
  (Node + MySQL) se a Railway for descartada; para produção, 4GB é mais
  confortável.
- Latência EUA ↔ Brasil é aceitável para AFD periódico (1,5MB a cada coleta).
- **Para o iDFace este VPS não é necessário**: o push aceita URL/domínio e a
  Railway pode receber direto (HTTPS). O VPS é só para o REP iDClass.

- **iDFace** alimenta o MultiPonto e outros softwares (inclusive controle de
